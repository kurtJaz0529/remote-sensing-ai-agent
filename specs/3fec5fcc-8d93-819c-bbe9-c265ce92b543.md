# 4. 文件所有权与版本交接
- 不建设GitHub协作空间。Notion统一承接任务、决策、结果和问题汇总；本地代码版本管理可使用Git，但不作为参与前提。
- 每个任务拥有独立工作目录和主写成员；跨目录修改提交文件/补丁及版本说明给云端Codex集成，避免覆盖。
- T03冻结最低可用工具与交接协议，其他成员据此开发。公共接口变更必须登记影响任务、兼容方式与新版本。
- 每次交付写明文件名、版本、哈希、适用环境和可用附件/获取方式；不假定云端可读取用户D盘。
- 各Agent完成批次后直接更新Notion对应任务页，不等到项目结束才汇总；无写权限时提供标准汇总文件由可写成员代录。

```yaml
task_id: T10

  static_or_mock: []
  real_software_run_ids: []
  evidence_manifest: null

```
接收者先检查输入引用/产物哈希/版本是否存在，再做评审；不得将“代码完成、mock通过、真实软件通过、回归通过”合并成一个模糊的完成状态。
会话开始读取AGENTS、当前任务、依赖的交接包与规格；会话结束提交此结构。上下文被压缩或客户端切换后从该结构恢复。
# 6. 本地执行互斥与恢复
- 三成员可并行研究和写代码，但首版只有一个本地执行协调器调度软件。
- desktop_lock覆盖所有GUI操作和截图；software_lock控制有会话状态的软件；project_lock防止同时写同一工程；run目录不可共写。
- 锁包含owner、run_id、进程ID、心跳和到期时间。锁过期先检查旧进程与产物，再决定接管，不能自动重复计算。
- 软件调用和截图分开排队；API计算完成后获取桌面锁，打开正确输出、检查标题/图层、截图并释放。
- 后续并发需有工具声明、许可数量、内存/磁盘预算与输出隔离验证。首先保证单机可靠，不先建设分布式Agent集群。
# 7. 启动顺序与每日协作
第一轮：本地Codex领取T01/T02；云端Codex领取T03；Gemini（Antigravity）先做T05/T06与T07设计，再按依赖承接方法/Skill/核验/报告。不能将该成员计作两个并行执行者。
每日或每个工作批次结束只汇总：新完成与证据、阻塞、接口变更、下批任务。各成员直接更新Notion对应任务；云端Codex核对总体进度和依赖，本地Codex同步真实运行摘要。
阻塞上报固定格式：现象→涉及任务/版本→已尝试及证据→需要的具体输入/决策→不受影响的可继续任务。
# 8. 给本地Codex的启动任务包
```plain text
你的角色：Windows真实执行与兼容性负责人。
先读总计划、01系统架构、03运行规则、05任务表及共同AGENTS草案。
第一批领取T01、T02；T03协议确定后领取T08、T09、T10、T11、T16。
1. 探测Windows、CPU/RAM/磁盘、ENVI/MATLAB/ArcGIS Pro版本与路径、Python/IDL环境、许可与扩展、桌面会话。
2. 只登记用户实验文件，建立manifest、哈希和缺失项，不修改原件。
3. 按冻结工具协议，先逐软件完成一个最小真实调用，再扩展方法。
4. 原生结果、参数、日志、重读检查、真实窗口截图必须关联run/step。
5. 不用历史笔记替代当前探测，不把云端mock结果当本机通过。
6. 输出environment.json、capabilities.json、input_manifest.json、验证证据与handoff。
7. 没有许可或接口时说明精确阻塞；不要自行换软件/算法来掩盖。
```

# 10. 给Gemini（Antigravity）的统一启动任务包
```plain text
你是同一个成员，兼任知识研究和方法/Skills/核验/报告开发。
第一批T05/T06资料与方法卡、T07验收矩阵；随后T12、T17–T23及T29，按依赖顺序推进。
1. 检索对应版本官方文档、教材、论文和可信实现；每条关键结论保留URL/DOI/章节、适用条件和待验证项。
2. 按冻结契约写方法包、8项Skill、独立数值检查和报告模板；不搜索下载新的实验影像。
3. 本机软件验证交本地Codex执行；你的方法和核验器交云端Codex交叉评审，不能自行宣布独立验收通过。

5. 每个任务/批次完成后，在Notion对应任务页记录完成内容、产物及版本、证据、验证、问题、下一步与经验。
6. 同一任务持续更新原记录；无Notion权限则生成标准汇总交可写成员代录，不声称已经同步。
```
