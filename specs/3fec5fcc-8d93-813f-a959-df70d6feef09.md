# 1. 建库目标与首批范围
数据库围绕“完成用户任务需要什么证据和操作能力”建设。第一批目标为约30–50个高价值来源、10–15张方法卡、3套软件能力清单、8个基础Skill、20–30条有证据的经验候选；这些是工作量估算，不是凑数量的验收要求。
按首批任务倒推资料。遥感百科、所有卫星产品和所有论文暂不全面收集。只处理用户文件不限制知识检索；采集官方文档/论文/代码不等于获取新的实验影像。

# 3. 论文与资料选择标准
- 每主题先选可靠教材/综述、方法原始来源、与用户场景匹配的验证案例各一类；能覆盖需求即停止扩张。
- 检索主题示例：maximum likelihood classification assumptions；ISODATA split merge convergence；spectral indices scaling offset；categorical raster resampling；post-classification smoothing accuracy tradeoff；remote sensing spatial validation。
- 纳入条件：作者/机构/DOI或稳定URL可追溯，方法和输入条件明确，参数和评价设计可解释，适用范围与当前任务匹配。
- 排除或仅记线索：仅有摘要却声称读过全文，博客搬运无原始出处，模型生成但无来源的公式，软件版本不明的操作视频，无法确认许可证的待集成代码。
- 文献结论用于方法依据，不直接变成软件接口事实。论文算法与软件实现可能不同，分别建卡。
- 遥感精度评价论文不能自动使课程练习获得统计推断资格；应检查采样设计和参考标签性质。
- 获取全文受限时记录“仅摘要已查”；不要求成员大量下载无权获取的资料，也不把缺失全文当作已读。

# 5. 证据状态必须分开
1. 来源权威程度：官方/论文/个人实测/社区/模型候选。
2. 适用性：软件版本、传感器产品、输入条件、许可、算法实现。
3. 验证状态：候选、来源核查、本机验证、失效/废弃。
官方资料也可能版本不适用；一次成功也不代表全范围支持。Gemini（Antigravity）不能把自己总结的条目标成“本机已验证”；只有真实运行证据能晋级该状态。

# 6. 从资料到可执行知识的操作
1. Gemini（Antigravity）先领取主题，登记已搜来源，防止三成员重复检索。
2. 每条关键结论给原文位置；将已知事实、推断、待核实项分开，保留矛盾。
3. 云端Codex检查schema、去重、版本过滤、知识冲突及方法前置条件。
4. 本地Codex用当前安装软件和用户数据小子集执行最小案例；必要的构造小数组仅用于验证软件边界，不作为替代实验数据。
5. Gemini（Antigravity）把研究结果实现为方法/Skill/核验/报告；云端Codex交叉审查来源及实现，本地Codex提供真实软件证据。同一成员的研究和开发不视为两个独立评审。
6. 通过后绑定工具和Skill，进入发布清单；未通过保留候选与原因。
7. 发布manifest固定来源revision、Skill、工具commit及测试记录；旧运行仍引用旧版本。
# 7. Agent如何调用知识库
- 解析任务类型、数据身份、软件版本、交付要求，形成检索条件。
- 首先查已发布Skill和本机能力表，硬过滤软件版本、许可、输入格式、产品级别。
- 精确匹配函数名/参数名/错误码，再全文检索；确有提升再加语义检索。
- 每阶段只加载当前Skill、相关方法卡、参数定义、已知错误和必要来源摘录；其余保存ID按需取。
- 检索结果返回知识ID、来源、适用条件、验证状态、冲突和对应工具；不能只返回不带来源的总结。
- 无匹配时依次查本机帮助、官方网页、论文或GitHub；研究结果进入候选区，经小实验验证才作为新调用依据。
- 运行时固定知识快照；紧急修正产生新的计划/知识revision并留痕。
- 本地快照可离线使用；Notion暂时不可用不阻断已经确认、所需知识齐备的任务。

# 9. 基于用户已有档案的第一批规则
- 类别编号冲突：必须显式映射，测试编号置换后语义比较不变。
- 诊断复评/参考ROI一致性被写成独立精度：强制评价性质字段和报告限定。
- PA/UA或混淆矩阵轴颠倒：使用非对称矩阵独立复算。
- 无坐标却报公顷：没有可靠尺度/坐标依据时禁止换算。
- 数值范围看似反射率：没有产品/比例证据时保留存储数值表述。
- 自写近似被当ENVI原生：implementation_kind与运行工具必须一致。
- 截图旧窗口：核对任务、步骤、时间、窗口/图层和真实产物。
- DOCX/PDF/统计来自不同版本：冻结manifest、统一报告源、重新导出与核验。
- 参数未提交：以实际参数/输出检查为准，不能凭成功退出判断。
