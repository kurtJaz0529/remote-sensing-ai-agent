# 2. 工程文件如何交付
- ArcGIS Pro：根据任务保存.aprx、图层/样式和依赖数据；需要时打包。换目录或重开后检查无损坏数据源；项目只引用缺失临时目录不算合格。
- ENVI：原生栅格/头文件、ROI、矢量/相关文件、参数及所支持的会话/任务定义；不同版本未必存在统一“工程”格式。若当前版本无适合的项目文件，以清晰的原生工作目录和一键/分步重放脚本交付，并在方案中说明。
- MATLAB：.m/.mlx等实际使用代码、配置、数据与输出、路径/环境说明；必要时MATLAB Project。不是每个任务都必须制造.mlproj，重点是可打开和可重跑。
- 统一reproduce说明：输入位置、依赖、命令、实际版本、预期产物、容差、运行时长口径和已知限制。不得把带用户机器绝对路径的工程直接当可移植交付。
- “能打开查看”和“能重新计算”分别验收；两者都应在交付清单中有状态。
# 3. 截图规范
必需截图点由任务文档和计划确定，通常包括输入识别/波段显示、关键参数或实际调用说明、关键中间结果、最终分类/指数、评价结果、工程/制图成果。
每张截图记录evidence_id、run_id、step_id、软件/版本、窗口标题/进程、图层或数据名、capture_time、显示的artifact_id、该产物哈希、截图文件哈希、说明、是否用于最终报告。
截图流程：取得桌面锁→打开本次实际输出→核对软件/文件/图层身份→等待渲染→截图→重读图片确认非空且内容正确→保存关联→释放锁。
- 软件导出的地图或图表可作成果图，但不能冒充软件操作窗口截图。
- API/脚本执行应报告真实调用方式；如果没有出现参数对话框，就不能写“逐项点击该对话框执行”。
- 实际界面操作的参数截图必须在执行时取得；结果展示截图可在产物生成后补拍，但标注它是结果展示，不能伪装成当时的操作证据。
- 旧窗口、空图、错误图层、被遮挡窗口不满足截图要求；需要重拍或明确缺失。
- 不开发产品GUI与使用专业软件窗口不冲突。锁屏或交互会话不可用时后台计算可保留，但截图任务等待/阻塞，不宣告整体完成。
# 4. 实验报告结构
1. 实验目标、要求与完成范围。
2. 数据来源、文件、传感器/产品信息、波段、单位、坐标及限制。
3. 环境、软件/工具和关键版本。
4. 处理方案与方法依据，明确样本和评价协议。
5. 实际操作步骤：目的、输入、参数、执行方式、输出、对应截图及检查结果。
6. 结果：图表、统计、分类/指数/变换、前后对比。
7. 核验：真实数据复算、逐类评价、未分类率、工程/矢量检查；区别诊断复评与独立评价。
8. 错误与修复：影响结果的实际问题和解决证据；失败分支与最终链区分。
9. 结论与适用边界：缺失数据、参考样本来源、未完成项。
10. 交付清单、复现入口、来源与附录。
报告从冻结的run manifest和结构化表生成，不让模型自由重填数值。模板负责类别顺序、单位、统计口径和引用；模型负责解释已验证事实。
DOCX/PDF由同一来源生成。PDF导出工具由T01确认（可用的Word/其他导出路径），不能仅改后缀；生成后检查页数、关键内容/表图/截图/中文字体和版式。无可用PDF能力时明确未完成，不能声称交付齐全。

# 6. 关键故障案例
T26至少覆盖：
- 类别编号置换但语义相同：映射后比较不变。
- 非对称混淆矩阵：能发现行列、PA/UA或分母颠倒。
- 没有CRS/像元尺度：拒绝无依据的真实面积换算。
- 同数值不同产品元数据：按正确比例/偏移分支处理，不依赖值域猜单位。
- ENVI参数未提交/默认值残留：实际参数或输出检查发现。
- 打开旧结果截图：不能被当作当前步骤证据。
- 报告读旧统计或错误类别列：版本/映射检查阻断。
- 已使用测试点调参：评价自动标记为开发/诊断用途。
- 计算中断、模型断线、重复提交、旧进程仍在：恢复先核对，不重复写工程。
- 许可不可用、文件损坏、磁盘不足：有明确错误状态，不靠重试耗尽预算。
构造数组只用于方法与边界测试，不用于伪造用户实验结果。
# 7. 归档和后续Agent接手
运行结束生成：
- manifest.json：全部交付及必要中间证据的相对路径、大小、哈希、来源step。
- run_summary.json：目标、实际链、最终结果、评价性质、已核验项、未完成项、版本与限制。
- [handoff.md](http://handoff.md)：后来者应先看什么、不要混用哪些版本、待修复问题、下次可执行入口。
- experience_candidates：每条候选关联真实事件，不覆盖既有经验。
默认保留用户原件、确认契约、最终产物、实际脚本/配置、日志、必需截图和验证证据。大型中间文件在确认可重建和保留策略后再清理；首版不自动删除用户文件。归档需在空目录恢复验证，损坏或遗漏要明确报告。
Notion同步运行摘要、结论、经验候选和证据索引；本机路径不是云端可访问链接。需要远端审查时显式导出证据包，不假设读者能打开本地文件。
# 8. 从经验到下一版能力
```mermaid
flowchart LR
    A["真实异常/有效做法"] --> B["候选经验与来源"]
    B --> C["限定触发条件与原因假设"]
    C --> D["最小复现与修复对照"]
    D --> E["规则/Skill/工具改动"]
    E --> F["回归与独立审查"]
    F --> G["发布新版本"]
    G --> H["观察效果/撤回"]
```
经验字段：现象、版本/数据条件、原始证据、原因假设、修复动作、前后结果、反例、适用范围、核验者、发布版本、撤回/替代关系。
- 模型总结只能进入候选；一次成功不直接普遍化，一次GUI异常先限定对应版本/窗口。
- 经验可成为提示、检查器、参数约束、恢复分支或Skill更新。优先把高频错误做成程序检查，减少每次消耗模型注意力。
- 更新不自动修改底层模型权重。首期提升来自检索、工具、流程和验证；微调不在首版范围。
- 新版本保留回滚。软件升级、方法变更或知识冲突时重新验证受影响能力，旧版本证据继续可查。
# 9. 如何衡量真实提升
固定案例集比较基线与更新版，控制数据、任务、模型配置和预算；至少记录：
正确完成率、严重结论错误数、首次成功率、重复错误率、人工干预次数、无效工具调用、模型Token/费用与总耗时、截图/交付完整率、复现成功率。
发布最低要求：必需产物和证据完整；无严重结论错误；指定回归全部通过；新增知识不降低已验证能力。效率目标先测基线再设，不凭空承诺提升百分比。
开发样例、回归案例和保留验收分开。保留参考答案/标签和评分细节不进入执行Agent检索库；一旦用于指导修复就转入回归，另留未见案例。若当前用户资料不足，先标记缺少泛化验收证据，不能靠反复优化同一实验声称普遍精通。
